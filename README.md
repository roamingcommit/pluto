# Pluto

Pluto is a simple trip planner built for the Software Development course with Nico Deblauwe. It gives a traveller one place to keep their trips and the activities planned for each trip.

Each user has their own trips. After logging in, they can create a trip, add dates and an optional hotel name, then plan activities within those dates.

## What the app does

- Register, log in and log out.
- List, view, create, edit and delete your own trips.
- View a trip's activities in date and time order.
- Create, view, edit and delete activities within a trip.
- Validate trip dates and keep activities within the trip's date range.
- Prevent a trip date change that would leave an existing activity outside the trip.
- Prevent users from accessing or changing someone else's trips and activities.
- Delete a trip's activities automatically when the trip is deleted.

The current scope is personal trip planning, not a booking service. Hotel is an optional text field on a trip. There are no separate Hotel or Country models, shared trips, or administrator roles.

## Models and relationships

| Model | Purpose and main fields | Relationships |
| --- | --- | --- |
| User | The account used to log in: name, email and hashed password. | Has many trips. |
| Trip | A journey: title, start date, end date, optional hotel name and `user_id`. | Belongs to one user; has many activities. |
| Activity | Something planned during a trip: title, start date and time, optional location and notes, and `trip_id`. | Belongs to one trip. |

`User → many Trips → many Activities`

The foreign keys connect these records: `trips.user_id` identifies the owner, and `activities.trip_id` identifies the trip. An activity's owner is determined through its trip.

## Requirements

- PHP 8.4 or a compatible newer PHP 8 release, with Laravel's required extensions and SQLite support.
- Composer 2.
- Node.js 22.12 or newer compatible with Vite 7, and npm.
- Git.
- Laravel Herd for the local setup below.

The app uses Laravel 13, Blade views, Laravel Breeze authentication, Tailwind CSS, Alpine.js and SQLite. Automated tests use Pest.

## Fresh local installation

These instructions are for a new checkout with an empty database. Run the commands from the project directory. Do not overwrite an existing `.env` or reseed a database containing work you want to keep.

1. Clone the repository into a directory served by Herd and install the dependencies:

   ```bash
   git clone https://github.com/roamingcommit/pluto.git
   cd pluto
   composer install
   npm ci
   ```

2. If `.env` does not exist, copy the example configuration:

   ```bash
   cp .env.example .env
   ```

   In `.env`, set `APP_NAME=Pluto`, keep `DB_CONNECTION=sqlite`, and set `APP_URL` to the local site address shown in Herd. Leave `DB_DATABASE` unset to use `database/database.sqlite`. Keep `.env` out of Git.

3. Generate the application key and create the empty SQLite file:

   ```bash
   php artisan key:generate --no-interaction
   touch database/database.sqlite
   ```

4. Create the tables, populate the demo data and build the frontend assets:

   ```bash
   php artisan migrate --seed --no-interaction
   npm run build
   ```

5. Make sure Herd is running and serving the project with PHP 8.4 or a compatible version. Open the site using Herd, log in, and select **My Trips**.

For frontend development, run `npm run dev` and leave it running while making styling or JavaScript changes. Herd serves the PHP application; a second PHP development server is not needed.

This is a normal user account for local demonstration, not an admin account. These credentials must not be used for a public deployment. A newly registered account starts with no trips.

The seeder is intended for an empty database. Running it again without resetting will try to create the same test email. `php artisan migrate:fresh --seed` deletes all existing tables and data before rebuilding them; use it only on a disposable database, never on a database containing trips you want to keep.

## Main routes

Trip and activity routes require login. Controllers check trip ownership, and scoped route binding ensures an activity belongs to the trip in its URL.

| Method | Path | Route name | Purpose |
| --- | --- | --- | --- |
| GET | `/trips` | `trips.index` | List the logged-in user's trips. |
| GET | `/trips/create` | `trips.create` | Show the new-trip form. |
| POST | `/trips` | `trips.store` | Save a new trip. |
| GET | `/trips/{trip}` | `trips.show` | Show one trip and its activities. |
| GET | `/trips/{trip}/edit` | `trips.edit` | Show the edit form. |
| PATCH | `/trips/{trip}` | `trips.update` | Save changes to a trip. |
| DELETE | `/trips/{trip}` | `trips.destroy` | Delete a trip and its activities. |
| GET | `/trips/{trip}/activities/create` | `trips.activities.create` | Show the new-activity form. |
| POST | `/trips/{trip}/activities` | `trips.activities.store` | Save a new activity. |
| GET | `/trips/{trip}/activities/{activity}` | `trips.activities.show` | Show one activity. |
| GET | `/trips/{trip}/activities/{activity}/edit` | `trips.activities.edit` | Show the activity edit form. |
| PATCH | `/trips/{trip}/activities/{activity}` | `trips.activities.update` | Save changes to an activity. |
| DELETE | `/trips/{trip}/activities/{activity}` | `trips.activities.destroy` | Delete an activity. |

There is no separate activity index page: the activity list is part of the trip detail page. Authentication routes are defined in `routes/auth.php`.

## Where to find the code

- `routes/web.php`: connects the trip and activity URLs to controller methods.
- `app/Http/Controllers/TripController.php`: trip validation, ownership checks and CRUD actions.
- `app/Http/Controllers/ActivityController.php`: activity validation, ownership checks and CRUD actions.
- `app/Models/`: the User, Trip and Activity models and their relationships.
- `resources/views/trips/` and `resources/views/activities/`: the Blade pages and forms.
- `database/migrations/`: table definitions and foreign keys.
- `database/factories/` and `database/seeders/DatabaseSeeder.php`: sample data generation.
- `tests/Feature/`: automated checks for application behaviour.

A request follows the route to a controller. The controller checks access, reads or changes models, and returns a view or redirect. `edit` displays a form; `update` saves its changes.

## Running tests

```bash
php artisan config:clear --no-interaction
php artisan test --compact
```

The checked-in `phpunit.xml` configures a separate in-memory SQLite database for tests. Do not override those test database settings with your normal database. The tests cover authentication, trip and activity behaviour, validation, ownership restrictions, relationships and demo seeding.
